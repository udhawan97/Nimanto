# Nimanto v0.5.1 — Say What You Need, Ask Before You Burn It

v0.5.1 is a fix release. It changes no schema, no domain policy, and no
boundary. What it changes is what the product tells a candidate at the moment
they need to know something, and whether the work they were doing survives the
telling.

Every item below came from an audit that drove the running product across nine
workbench sections, five viewport widths, two browser engines, and the failure
paths — not from reading the source. Each was reproduced, fixed at the shared
cause, and re-run under the exact flow, fixture, viewport, theme, and input that
exposed it.

## Getting back in

Sign out was a one-way door. The private launch key arrives in a URL fragment
that the workbench scrubs on sign-in, so signing out, deleting the workspace, a
bookmark, and the workbench URL printed in the operations guide all reached an
entry screen whose two buttons were disabled with nothing saying why. The gate
stays — the API enforces it independently — but the screen now names the key it
needs and the file that holds it, bound to both controls so assistive technology
reads it from the button rather than from somewhere nearby.

## Deciding on evidence

Rejecting a claim was a single unlabeled grey glyph beside an identical one, and
it was final: `confirmEvidence` and `rejectEvidence` both move a claim out of
`pending` and nothing moves it back. It is the decision the whole product is
built around. Keep and discard are now named controls of equal size with
distinct treatments, rejection asks once before it writes, and a rejected row
says the decision is final. This is the rule the codebase already applied to
cancelling a schedule and to erasing a workspace, reaching the screen where it
matters most.

## Confirming a consequential move

Three `window.confirm` calls became one in-product confirmation. A browser
dialog can only offer OK and Cancel, which names neither of two consequential
outcomes in a product that is otherwise exact about the difference; it carries
the origin in some browsers; and once a browser has been asked to suppress
dialogs it returns false immediately, turning the control into a silent no-op
with nothing on screen to explain it. The prompt sentences are unchanged. Only
the chrome and the button names are ours, and cancelling returns focus to the
control that was pressed.

## Keeping your place

Every successful action dropped keyboard focus to `<body>`. One global `busy`
flag disables 41 controls for the duration of a mutation, and disabling the
focused element is what hands focus to the document; the failure branch always
had the alert region to land on and status moves name their own successor, but a
plain success had nowhere to go. The mutation coordinator now remembers the
control that started the work and gives focus back, falling back to the section
container when the commit replaced that control. The failure path and the
deliberate successors are unchanged.

## Seeing the whole pipeline

The application board is five real stages, so below roughly 1560 px it is wider
than the content column — 634 px hidden at 1024 px, with two stages entirely
outside the viewport and a third clipped mid-word. Scrolling always worked;
nothing said so, the container could not take focus, and confirming a move could
send a card to a stage the candidate could not see while focus followed it out.
The board is now a focusable region that states its hidden extent in words, and
a move scrolls its destination into view.

Alongside these: a disabled **Approve** says it is waiting on assurance, the
Applications header stops offering to track "another" role when nothing is
tracked, and quick navigation moves `aria-activedescendant` with its highlight
so arrow-key selection is announced rather than merely drawn.

## Keystrokes that went nowhere

Section focus is scheduled an animation frame after the section changes, so it
could land after the candidate had already started typing in the section they
navigated to — taking focus off the field and sending the rest of the keystrokes
nowhere. The destructive deletion phrase is the worst place for it: characters
vanished mid-entry and the confirmation simply stayed disabled. Focus is now only
moved while it is still outside the section. The release journey's deletion
receipt test failed two runs in six at v0.5.0 for exactly this reason; it passes
ten in ten now.

## Throttling is not a failure

Found while verifying the rest. The API's error handler maps any error whose
message is not a SCREAMING_CASE domain code to `INTERNAL_ERROR` with status 500.
A rate-limit rejection from `@fastify/rate-limit` carries a human-readable
message and its own status, so its `429` was rewritten as a `500` — including on
the static `/health` route. The workbench's connection probe drew the only
conclusion available to it and displayed **"Connect the local service."**,
sending the candidate to restart a backend that was running when the only remedy
was to wait.

A framework rejection now keeps the status it set, `429` has a named
`RATE_LIMITED` code, a `Retry-After` header, and copy that says to wait, and the
ceiling bounds a runaway loop rather than a person: 180 requests a minute is
three a second, and one candidate move costs a write plus a dashboard refresh on
top of the liveness poll. The release journey exhausted that budget on its own,
which is why the WebKit suite's tail failed at v0.5.0.

## Verification

- `pnpm check` — formatting, spelling, types, and 237 unit tests across eight
  workspaces.
- `pnpm test:e2e` — 15 of 15 WebKit journeys, in about 21 seconds. The same
  suite at v0.5.0 finished with four to five failures in roughly 1.4 minutes.
- Seven new regression tests at public seams: focus restoration in the mutation
  coordinator, combobox wiring in quick navigation, throttling status in the
  API, section focus yielding to input, and four new WebKit journeys covering the
  entry screen, the pipeline, the claim decision, and the gated controls.
- Two existing journeys were rewritten to click the real confirmation controls.
  One of them carried a comment asking for exactly that if the dialog ever moved
  in-product.

## Upgrade

v0.5.1 introduces no schema migration. Startup remains on additive, idempotent
schema version 3. Stop the API, copy `.nimanto-data/`, update to the exact
v0.5.1 source archive or tag, and reinstall the locked dependency graph:

```bash
corepack enable
pnpm install --frozen-lockfile
pnpm dev
```

No stored record changes shape. A claim already in `rejected` stays rejected —
the new confirmation guards the transition, it does not reopen it.

## Still out of scope

Unchanged from v0.5.0: no employer screening, no hiring-probability estimate, no
legal advice, no connected-account sender, no signed installer or desktop
binary, and no claim that any company sponsors transfers today.

## Known limits

The audit that produced this release did not exercise Stored history, Approved
actions, Local activity, scheduled board refresh, allowlisted URL intake,
invitation acceptance, real document import, physical touch devices, or a screen
reader. Those surfaces are unchanged by this release and remain as verified at
v0.5.0. Contrast was not re-measured; this release makes no new accessibility
compliance claim.
